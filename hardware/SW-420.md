# SW-420 vibration / impact sensor

Detects an **impact event** — the AeroHalo concept being: possible aircraft or
GSE contact, therefore inspection required. It measures disturbance, not force,
direction or location, and nothing in the system claims otherwise.

Status: **working and verified live** — real taps have produced
`CRITICAL Abnormal vibration detected` events on the board.

---

## Wiring

```
SW-420 VCC -> UNO Q 3.3V
SW-420 DO  -> UNO Q D10
SW-420 GND -> common GND
```

Digital output only. The module's on-board comparator does the thresholding;
its small potentiometer sets how hard a knock counts.

---

## Polarity is learned, never assumed

SW-420 boards ship in **both senses** — some idle HIGH and pull LOW on
vibration, others the reverse. Hard-coding either one is a coin flip, so the
firmware works it out at boot:

1. Watch D10 for a settling window (`VIB_CAL_MS`, 3 s).
2. Any change during the window **restarts** it, so a board being knocked about
   while booting stays uncalibrated rather than learning the wrong polarity.
3. The level it rests at becomes `idle`. Anything else is a disturbance.

The learned result is published as `vibration.polarity`:

```
"unverified"  | still calibrating, no events accepted
"active-high" | idles LOW,  pulses HIGH on impact
"active-low"  | idles HIGH, pulses LOW  on impact
```

**This unit calibrated as `active-high` (idle LOW).** That is measured, not
assumed, and it is re-learned on every boot.

While `unverified`, no vibration event can fire at all.

---

## Debouncing

A single tap rings the switch many times. Two mechanisms keep one tap to one
event:

- **`VIB_DEBOUNCE_MS` (400 ms)** on the MCU — further edges inside this window
  do not create a new event.
- **A 2 s log window** on the Linux side, so a burst of taps is one line in the
  timeline rather than fifty.

### The phantom impact at power-on

Worth knowing, because it produced a HOLD before the demo could start. The
debounce timestamp began at zero, so the first evaluation after calibration
looked like an edge that had happened long ago and fired immediately. The fix:
start the debounce window at the moment calibration completes, and discard any
event detected before the idle level was known — anything "detected" before we
knew what idle looked like was meaningless by definition.

---

## Fusion behaviour

- A vibration event contributes **+55** to the risk score.
- It **forces HOLD** regardless of the score. This is a deliberate override:
  a possible impact means a human inspects the area, full stop.
- The HOLD is fed from the **latch**, not the instantaneous line level, so it
  survives the tapping stopping. Vibration ending is not evidence that nothing
  was hit.
- Clearing it needs an explicit operator reset, and the reset is refused while
  vibration is still active.

## Events

```
INFO      SW-420 online, idle level LOW
CRITICAL  Abnormal vibration detected. Possible impact, inspection required
```

## Troubleshooting

| Symptom | Cause |
|---|---|
| stays `unverified` | the board is being disturbed continuously, so the settling window keeps restarting |
| fires constantly | module pot too sensitive, or the sensor is sitting on something that hums |
| never fires | pot too insensitive; or it is genuinely mounted somewhere rigid |
| fired once at power-on | should no longer happen — see the phantom impact note above |
